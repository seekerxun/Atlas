# 元数据规范

Atlas 管理的项目里，只有两处需要人和 AI 手写：

1. **每个 md 开头的 frontmatter**——分散，跟着文件走
2. **`路线/*.yml`**——集中，只有项目主人写

其余全部由程序扫描生成。机器读的词表在 [词表.yml](词表.yml)，本文是它的人读版本，冲突以词表为准。

## 总规则

> 一个字段进 frontmatter，只有两个理由：**要么它连向另一个东西**（条目、机制、工具、资产），**要么你要拿它筛选分组**。其余全部留在正文。

技能的倍率和预算、NPC 的背景故事和设计意图，都是正文。守不住这条，frontmatter 会长成比正文还长的表单，然后没人填。

---

## 一、必填只有两行

```yaml
---
类型: NPC
状态: 草案
---
```

**库和分组由目录推导，不用写。**文件在 `内容/W-001-断武之境/NPC/` 下，程序就知道它属于内容库、分组是 `W-001`。移动文件即改变归属，这正是你想要的行为。

极少数情况需要覆盖（放在某个世界目录下但其实是公共的），显式写一行 `分组: 公共`。

根目录的 `AGENTS.md`、`README.md`、`项目.yml` 是项目骨架，不是条目，**不要求 frontmatter**，也不判孤儿。

### 类型

策划层和通用类型由 Atlas 固定，**内容层类型由每个项目在 `项目.yml` 里声明**——不同项目的内容实体本来就不一样。

词表是封闭的，要细分用 `标签`，不要扩表。类型一旦超过十几种，卡片配色和层级规则就没法看了。

### 状态

`草案` → `待审查` → `可原型` → `已定稿`，不用了标 `废弃` 保留记录。项目可以在 `项目.yml` 里换一套。

## 二、按需要加的字段

```yaml
---
类型: NPC
状态: 草案
摘要: 灰烬教团的圣徒，同时是王国通缉犯和某个异常物的宿主
位阶: 2
机制: [异常适应, 活体收容]
关联:
  所属势力: [F-W001-003 灰烬教团]
  敌对: [F-W001-001 王国]
  出现在: [S-W001-001 断武试炼]
资产:
  人设: [资产/W-001-断武之境/NPC-W001-001/立绘-v3.png]
工具: [工具/numeric-workbench]
数据: [数据/W-001-装备表.csv]
标签: [治疗, 异常宿主, 条件招募]
---
```

| 字段 | 程序拿它做什么 |
|---|---|
| `摘要` | 中景卡片上显示的一行字。**画布能不能看懂全靠它**，值得写 |
| `位阶` | 筛选、排序 |
| `机制` | 连到机制权威文档；名字不存在直接报错 |
| `关联` | 卡片内列成一行行；选中卡片时画一跳线 |
| `资产` | 卡片缩略图 |
| `工具` | 认领工具——没人认领的工具会被报成孤儿 |
| `数据` | 指向表文件 |
| `代码` | 文档与代码对应 |
| `标签` | 搜索筛选 |

### 写法只允许一种

YAML 同一件事有好几种写法，而 Atlas 的解析器是零依赖手写的——写法一多，**校验会假装通过**（实测踩过三次）。所以规范收紧成一种：

```yaml
机制: [异常适应, 活体收容]        # ✅ 列表一律行内
资产:
  人设: [路径1, 路径2]            # ✅ 嵌套一层 + 行内列表

机制:                            # ❌ 不要用 - 多行列表
  - 异常适应
资产:
  人设:
    - 路径1                      # ❌ 嵌套里也不要
```

- 列表一律写成 `[a, b]`
- 嵌套最多一层，值仍然是行内列表
- 写错不是"宽容处理"，是直接报 E10

### 五条配套规矩

1. **编号不写进 frontmatter。** 文件名前缀就是编号：`NPC-W001-001 灰烬修女.md`。一个东西不要有两个名字。
2. **关系只声明一次，谁具体谁声明。** NPC 声明所属势力、出现在哪个副本；势力和副本不反列。反向关系（"被谁引用"）由程序算出来，显示在卡片角标上。
3. **受控词表：一份权威名单 + 一个引用它的字段。** 项目在 `项目.yml` 里声明：

   ```yaml
   受控词表:
     - 名字: 机制
       文件: 策划/机制/机制目录.md
       段落: 现有机制
       取法: 表格首列      # 或 标题
       引用字段: 机制
   ```

   引用字段里的值必须在名单里，否则报 E05。"同一个概念全库同一个名字"这条规矩从此由程序执行，不靠自觉。想加第二份名单（术语表、状态清单、接口列表）就在列表里多写一条，**不用改代码**。
4. **`关联:` 的关系名是开放的**，想加一种关系不用改程序，程序只检查目标存在。
5. **单条 `关联` 不超过 8 项。** 超了说明这个条目该拆，或者那是张表。

### 实验性字段放 `扩展`

```yaml
扩展:
  画师: 老李
  出图进度: 线稿
```

程序不认识也不报"未知字段"，只当附加属性显示在展开的卡片上。等某个字段稳定了、确实要参与校验或画线，再提拔成正式字段——那时跑一次批量迁移，不用手改。

## 三、正文怎么写

frontmatter 之下照常写，程序不读正文，只抽 `[[双链]]` 当软引用（软引用不画线，只在卡片里列出来）。

双链支持 `[[名]]`、`[[名|显示名]]`、`[[名#标题]]`、`[[名#标题|显示名]]` 和只跳本篇标题的 `[[#标题]]`；表格里的显示名分隔写成 `\|`。画布阅读时它们是可点的链接：跳到那张卡片，带 `#标题` 的再滚到那个标题（按标题文字匹配，`[[名#父#子]]` 取最后一段）。找不到的名字只显示文字并标成未找到。

**不要把字段锁进 ```text 围栏。**围栏里的东西程序读不到、Obsidian 不认、没法筛选。该上 frontmatter 的提上去，其余摊开写成正文小节。

## 四、批量改字段怎么办

这是"1000 个条目加一个字段"的答案：

```bash
atlas 迁移 --加字段 阵营=中立 --筛选 类型=NPC
atlas 迁移 --改名 旧字段=新字段
```

因为 frontmatter 是严格格式，批量操作是安全的、可预演的（`--演习`）。**这正是把字段从正文提到 frontmatter 的核心理由**——锁在正文里的字段只能手改。

另外，新字段不填就是没有，老条目根本不用动。真正需要批量改的场合比你想的少。

## 五、什么不该是 md

| 内容 | 格式 | 为什么 |
|---|---|---|
| 有故事、有图、会被反复引用的实体 | **一实体一 md** | 九成内容是正文；单独 diff 看得清；AI 一次只改一个文件 |
| 成批、只有数字的行（装备、掉落、小兵、词条） | **CSV**，一行一条，UTF-8 | 文本可 diff，脚本好改，加列就是加一列 |
| 你要浏览和筛选的汇总 | **程序生成的视图**，要看可导出 xlsx | 视图是派生物，源始终只有一个 |

**不要用 Excel 当源数据**：二进制没法 diff，出问题不知道谁改的；AI 靠库读写容易静默出错；两处同时改必冲突；格式和公式会混进数据。Excel 只能是导出物。

按"**有没有正文和图**"分，不按数量分。真到上千个的多半是小兵和词条，那是表里的行；有立绘、有背景故事的实体，几百个也撑得住一条一个 md。

两者混在一起时（一个 NPC 既有故事又有一堆数值）：md 存故事和导航字段，数值那行在表里，md 用 `数据:` 指过去，表里有一列 `编号` 指回来。一对一对上，两边都不重复。
