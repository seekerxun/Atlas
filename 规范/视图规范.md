# 视图规范

制作不同外观时，遵守 [主题制作规范](主题制作规范.md) 中的共享功能与验收要求，尺寸、排版和动效由主题决定。

本页的容器、影卡和连线等呈现方案是设计参考，不是所有主题的外观限制；当前功能边界以主题制作规范为准。

## 一条总原则

> **用"包含"代替"连线"。**

毛线球的成因是所有关系都用线表达，而线在密集图里天然不可读。把大部分关系变成"谁装在谁里面"，线就只剩下极少数真正需要的。

---

## 五个视图

一个应用，五个独立画布，不混在一起：

| 视图 | 画什么 | 形态 |
|---|---|---|
| 路线 | 生产流程 | 流程图，可编辑，唯一有大量连线的视图 |
| 策划 | 规则层文档 | 容器：域 → 文档卡 |
| 内容 | 实例层实体 | 容器：分组 → 类型 → 实体卡 |
| 创意 | 未立项的点子 | 松散卡片墙，不校验 |
| 资产 | 图和产出 | 缩略图网格，按实体编号聚合 |

**策划和内容分开两个区。**内容引用策划（NPC 调用机制、副本引用数值规则）时不画长线，在内容区里显示成影卡，双击跳到策划区并聚焦。跳转保留返回栈。

---

## 容器从数据来，不是手画的

大卡片不是你手动圈出来的分组，而是直接对应目录和字段：

```
内容视图
  └ 分组卡（W-001 断武之境）        ← 来自主分组维度
      └ 类型分组（NPC · 23）         ← 来自 类型 字段
          └ 实体卡（灰烬修女）        ← 一个 md
              └ 字段、关系、缩略图     ← frontmatter
```

好处是你永远不用维护布局结构。新建一个 NPC，它自动出现在该出现的盒子里。

---

## 影卡：一个东西可以出现在很多地方，但只有一个本体

一个文档被多处引用时，在每个引用方内部放一张**影卡**，而不是拉一根线过去。

- **主卡**：在它的归属容器里，一个实体只有一张
- **影卡**：虚线边框 + 角标，表示"这是别处的东西"

两者必须在视觉上分开。否则画布会骗你：你以为有 5 个灰烬修女，其实只有 1 个。

- 改影卡就是改本体（像 Figma 的组件实例）
- 双击影卡跳回主卡
- 影卡角标写 `被 3 处引用`，展开列出引用方

**反向关系不画线，在卡片里列成一行行。**

---

## 语义缩放：缩放改变的是"显示什么"

这是无限画布能不能用的关键。一千张卡片，纯几何缩放只会换一种糊法。

| 层级 | 看到 | 每张卡显示 |
|---|---|---|
| 远景 | 视图全貌 | 容器名、条目数、状态分布、未认领数量 |
| 中景 | 分组 / 域 | 名字、`摘要`、代表图、健康状况 |
| 近景 | 实体卡 | 名字、缩略图、状态、关系数量 |
| 展开 | 单卡展开 | 全部 frontmatter 字段、关系列表、资产、正文摘要 |
| 打开 | 文档本体 | 交给 Obsidian 或编辑器 |

核心保留条目查看、阅读、关闭和画布状态；主题决定卡片大小、各缩放层显示什么，以及详情以居中卡片或侧边面板等形式呈现。单纯阅读和关闭不能改写已保存的节点位置。

**切换导航必须保留当前缩放与平移，所有主题共用这一规则。** 初次进入时设置阅读视野；只有主动缩放、点击「全局」或定位条目等操作才调整视野。

字号补偿、缩放阈值和长标题处理由主题决定。石墨采用 50% 以下随容器缩小的方式，这不是其他主题必须遵守的尺寸规则。

中景那一层完全依赖 `摘要` 字段——这是它值得写的唯一理由，也是充分理由。

---

## 关系功能与默认连线

核心保留路线步骤的流程关系和条目关联。石墨只绘制路线流程线，普通引用通过高亮呈现；其他主题可设计自己的连线与高亮方式，不改变关系的含义和编辑功能。

关系保留在卡片内的列表中，例如 `出现在 → S-W001-001 断武试炼`，点击可跳转或高亮对应条目。

---

## 每个容器底部有一个「未认领」抽屉

没有归属的东西不藏在体检报告里，直接堆在对应容器底部：

- 孤儿资产（没挂到任何条目的图）
- 孤儿工具（没有任何文档声明使用的脚本）
- 缺 frontmatter 的 md
- 放错位置的文件

你一眼就看见"这个世界有 12 张图没挂上"。

这引出画布的核心动词：

> **认领** —— 把未认领区的东西拖进某张卡片，程序就往那篇 md 的 `资产:` 或 `工具:` 里写一行。

`产出/` → `资产/` 的挑选，也是同一个动作。

---

## 路线视图的编辑

这是唯一需要手编的结构，尽量别让人去改 yaml：

| 操作 | 写回 |
|---|---|
| 拖卡片 | `.atlas/布局.json`，**不进 yml** |
| 从卡片右侧圆点拖到另一张卡 | `next` 加一条 |
| 点那条线 | `next` 去掉一条 |
| 展开卡片里「删掉这一步」 | 删这一步，指向它的线一并断开。**删除不放在卡片上**，误点代价太大 |
| 路线标题下「+ 加一步」 | 新建步骤 |
| 展开卡片里点标题 / 护栏 | `title` / `note` |
| 展开卡片「＋ 挂一篇文档」 | `docs`，从候选列表挑，不用手打路径 |
| 展开卡片里加工具 / 产出 | `tools` / `outputs` |
| 顶栏「＋ 新路线」 | 新建一个 yml |

yml 由程序按固定模板重写，**不做 YAML 往返**（往返会丢注释、打乱顺序），
文件开头的注释保留。始终保持十几行、人能读、git 能 diff。

**连线要挡成环。**路线是有向无环图，允许成环等于允许"第 3 步回到第 1 步"这种
读不出顺序的图，那它就退化成引用图了。

---

## 画布上的东西一律不可选中

拖画布时如果把卡片里的文字选中了，拖拽手感立刻就毁了。`#台` 整个 `user-select: none`，
展开卡片的详情、未认领抽屉、搜索框、挑选框单独恢复成可选。

## 重绘要清干净

每次重绘都得把上一轮生成的元素全删掉，**包括那些不起眼的装饰层**（标题、编辑条）。
漏一个，它就会一轮叠一层，看起来像字重影——这个 bug 出现过一次，漏的是编辑条。

## 撤销靠文件快照，不靠逆操作

每个写盘接口返回「改之前的全文」，画布压栈，撤销就是把它写回去。
不要给每种操作单独写逆操作——那是 bug 的温床，而且每加一种编辑就得再写一遍。

快照还有个隐性好处：撤销结果和原文逐字节一致。按模板重新序列化会留下引号、
空行这类痕迹，在 git diff 里看着像改过，实际没改。

撤销前必须比对 mtime。对不上说明别人动过这个文件，中止——
撤销覆盖掉别人的改动，比不能撤销糟糕得多。

## 两个工程约束

1. **必须有本地服务才能写盘。** 静态 HTML 双击打开写不了文件。形态是 `atlas serve`，只绑 127.0.0.1，浏览器打开。
2. **写回前比对文件修改时间。** 你在画布上拖的时候 AI 可能正在改同一个文件，不一致就提示重新扫描，绝不静默覆盖。

写回只允许改 frontmatter 区块里的指定字段，不碰正文。

---

## 布局怎么存

```
.atlas/布局.json
```

- 手动拖过的卡片记住位置
- 没拖过的自动排（容器内紧凑网格）
- 新增一个条目不该把你摆好的版面搞乱
- 删掉布局文件就全部回到自动排列

---

## 画布不是唯一入口

搜索永远是最快的路径。**画布回答"这是什么、周围有什么"，搜索回答"我要的那个在哪"。**两者并存，任何视图里按 `/` 直接搜。
